# Trace Specification & Tree API Contract

This specification documents the backend execution trace structure, the op-log request model, visual role mappings, hole policy, and API error formats for the Algorithm Laboratory simulation suite.

---

## 1. Request Models

The `/tree` endpoint operates in two mutually exclusive modes: **BST mode** (stateful history replayed via an op-log) and **Binary mode** (array-based level-order representation).

### 1.1 BST Mode: Op-Log Request Shape (`tree_type="bst"`)

BST operations maintain deterministic node identities statelessly through an append-only operation log.

- **Node Identity Rule**: The `id` of any node in the tree strictly equals the 0-indexed position `i` of the inserting op (`{"op": "insert", "value": ...}`) in `ops`. Node IDs are immutable and invariant across subsequent deletions and rebalances.
- **Duplicate Rule**: Inserting an already existing value into the tree is rejected with HTTP 400 (`field: "new_value"` or `field: "ops"`). Re-inserting a value that was previously deleted is permitted; it receives the ID of the new insert operation.

```json
{
  "algorithm": "bst_insert",
  "tree_type": "bst",
  "ops": [
    {"op": "insert", "value": 50},
    {"op": "insert", "value": 20},
    {"op": "delete", "value": 20},
    {"op": "insert", "value": 80}
  ],
  "new_value": 60
}
```

#### Deprecated Shim: `values` Array
For backward compatibility, requests supplying a legacy flat array `"values": [50, 20, 80]` are automatically converted by the backend into equivalent insert ops:
```json
[
  {"op": "insert", "value": 50},
  {"op": "insert", "value": 20},
  {"op": "insert", "value": 80}
]
```

---

### 1.2 Binary Mode: Array Shape (`tree_type="binary"`)

Binary mode represents trees via standard array layout:
- Root at index `0`.
- Left child of index `i` is at index `2i + 1`.
- Right child of index `i` is at index `2i + 2`.
- Parent of index `k > 0` is at `(k - 1) // 2`.

**Constraints**:
- **Prohibition of `ops`**: Because an op-log cannot encode null holes in fixed tree geometry, passing `"ops"` or `"values"` when `tree_type="binary"` is strictly rejected with HTTP 400 (`field: "ops"` or `field: "values"`).
- **Required Field**: Binary mode endpoints must provide an `"array"` field (e.g. `[10, 20, 30, null, 40]`).

```json
{
  "algorithm": "bst_traverse",
  "tree_type": "binary",
  "array": [10, 20, 30, null, 40],
  "order": "inorder"
}
```

#### Hole Policy & Orphaned Descendants
If an element in the array is `null`, any non-null slots at positions that descend from that `null` slot are orphaned (they have no structural parent).
- **Policy**: Orphaned descendants are dropped and not instantiated as nodes.
- **Reporting**: Dropped nodes are appended to a `"warnings"` list returned in the response:
  ```json
  "warnings": [
    "Orphaned descendant array[3] = 30 dropped because ancestor at array[1] is null"
  ]
  ```

---

### 1.3 Structural Comparison & Mirror Mode (`algorithm="bst_mirror"`)

The `bst_mirror` algorithm compares two trees (`tree_a` and `tree_b`) recursively. Each tree spec can independently be either BST op-log or binary array.

- **Modes**:
  - `mode="mirror"`: Tree A mirrors Tree B iff `root_a.val == root_b.val`, `left(A)` mirrors `right(B)`, and `right(A)` mirrors `left(B)`.
  - `mode="identical"`: Tree A equals Tree B iff `root_a.val == root_b.val`, `left(A)` equals `left(B)`, and `right(A)` equals `right(B)`.
- **Response Format**:
  ```json
  {
    "steps": [...],
    "final_tree_a": { "nodes": [...], "root_id": 0 },
    "final_tree_b": { "nodes": [...], "root_id": 0 },
    "verdict": {
      "is_match": true,
      "first_mismatch": null
    },
    "warnings": []
  }
  ```

## 2. Standard Error Format

Every error generated by the API—including bad inputs, schema mismatches, duplicate inserts, absent deletions, and unhandled exceptions—strictly conforms to:

```json
{
  "error": "<Descriptive error message>",
  "field": "<target_parameter_or_system_scope>"
}
```

Common field values:
- `"new_value"`: Missing, non-integer, or duplicate insert value.
- `"delete_value"`: Missing, non-integer, or absent delete value.
- `"target_id"`: Missing or absent node ID in `bst_height_depth`. If `target_id` is provided, the query searches exclusively by node ID; it returns HTTP 400 with `field: "target_id"` if absent, without falling back to `target_value`.
- `"target_value"`: Missing or absent target value in `bst_height_depth` (used only when `target_id` is absent).
- `"ops"`: Malformed op list, missing op fields, or forbidden in binary mode.
- `"array"`: Missing or invalid array in binary mode or array_to_tree.
- `"tree_a"`, `"tree_b"`: Missing, malformed, or invalid tree specification in `bst_mirror`.
- `"mode"`: Invalid comparison mode (must be `'mirror'` or `'identical'`).
- `"order"`: Invalid traversal order.
- `"tree_type"`: Invalid tree model (must be `'bst'` or `'binary'`).
- `"algorithm"`: Missing or unknown algorithm.
- `"body"`: Non-JSON or malformed HTTP request payload.
- `"request"`: HTTP-level errors such as 405 Method Not Allowed (e.g. GET /tree).
- `"server"`: Unexpected server error (HTTP 500 returns fixed message "Internal server error" and logs full traceback server-side).

## 3. Step Schema & Role Mappings

Every animation step generated by simulation algorithms conforms to the `make_step` trace specification.

### 3.1 Step Object Schema (Standard Single-Tree)

```json
{
  "type": "compare",
  "snapshot": {
    "nodes": [
      {
        "id": 0,
        "label": "50",
        "sublabel": null,
        "parent_id": null,
        "side": null
      }
    ],
    "root_id": 0
  },
  "annotation": "Human-readable explanation of the current operation",
  "highlighted": [],
  "comparing": [0],
  "rotating": [],
  "pruned": [],
  "new_node": [],
  "selected": [],
  "payload": {
    "path": [0]
  }
}
```

#### 3.1.1 Search and Insertion Path (`payload.path`)
- **Format**: `payload: { "path": [node_id_0, node_id_1, ...] }`
- **Semantics**: An ordered list of ancestor node IDs visited so far from the root down to the current node (`root` first).
- **Invariants**:
  - `path[0]` is always the root node (`parent_id == null`).
  - For each `i > 0`, `node(path[i]).parent_id == path[i-1]` (strictly forms an ancestor chain).
  - On `compare` steps during insertion and deletion search, `path` ends at the node currently evaluated.
  - On the final `insert` step, `path` ends at the parent of the newly attached node, allowing the client to keep the full path lit.

### 3.2 Dual-Tree Step Schema (Mirror & Structural Comparison)

Algorithms comparing two trees concurrently (`bst_mirror`) emit dual snapshots and suffixed role arrays (`_a` and `_b`):

```json
{
  "type": "mirror_compare",
  "snapshot_a": { "nodes": [...], "root_id": 0 },
  "snapshot_b": { "nodes": [...], "root_id": 0 },
  "annotation": "Comparing A:10 with B:10 — values equal",
  "comparing_a": [0],
  "comparing_b": [0],
  "matched_a": [],
  "matched_b": [],
  "mismatch_a": [],
  "mismatch_b": []
}
```

### 3.3 Visual Role Mapping (`DEFAULT_ROLES`)

The visualizer consumes semantic role arrays populated automatically from `node_ids`:

| Step Type | Primary Role Array | Meaning |
|---|---|---|
| `compare` | `comparing: [id, ...]` | Nodes currently participating in a comparison/search |
| `visit` | `highlighted: [id, ...]` | Node currently visited during traversal |
| `insert` | `new_node: [id]` | Newly attached node in tree |
| `create_node` | `new_node: [id]` | Node instantiated from array/input buffer |
| `delete_leaf` | `highlighted: [id]` | Leaf node designated for direct removal |
| `delete_single_child`| `highlighted: [id, child_id]` | Single-child node and child being promoted |
| `delete_two_children`| `highlighted: [id, succ_id]` | Two-child target and in-order successor to relink |
| `delete_done` | `highlighted: [id]` or `[]` | Completion of deletion; highlights new subroot/child |
| `reuse_node` | `highlighted: [id]` | Reusing existing prefix/node (trie) |
| `hash_compute` | `highlighted: [id]` | Slot computed during hashing |
| `probe` | `comparing: [id]` | Probing collision slots in open addressing |
| `mismatch` | `pruned: [id]` | Mismatched branch in pattern search |
| `prune` | `pruned: [id]` | Pruned search branch (backtracking / branch & bound) |
| `expand` | `highlighted: [id]` | Expanding frontier node |
| `call` | `new_node: [id]` | Recursive stack frame invocation |
| `dp_fill` | `new_node: [id]` | Table cell / subproblem value committed |
| `select` | `selected: [id]` | User-selected or inspected node |
| `mirror_compare` | `comparing_a`, `comparing_b` | Dual-node inspection in mirror comparison |
| `struct_compare` | `comparing_a`, `comparing_b` | Dual-node inspection in identical structural check |
| `mirror_match` | `matched_a`, `matched_b` | Nodes or dual-null positions successfully matched |
| `mirror_mismatch` | `mismatch_a`, `mismatch_b` | Position or value mismatch between Tree A and Tree B |

## 4. Deletion Protocol Details

BST node deletion strictly maintains node identity and pointer integrity:
1. **Search Phase**: Comparisons begin at the root node. The node being evaluated is placed in `comparing: [current.id]`.
2. **Absent Deletion**: If the target value does not exist in the tree, the request is rejected with HTTP 400 (`field: "delete_value"`).
3. **Two-Child Relinking**:
   - The in-order successor (leftmost node in the right subtree) is located.
   - The successor's node is physically relinked into the target node's position.
   - The successor preserves its original `id` (e.g. `succ_id = 3`), while the deleted node (`current.id`) is unlinked and removed.
   - The target node's value is never overwritten with the successor's value.
4. **Completion Step**: Deletion ends with a `delete_done` step highlighting the resulting position.
