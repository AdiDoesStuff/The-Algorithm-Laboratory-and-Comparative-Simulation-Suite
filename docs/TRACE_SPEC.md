# Trace Specification & Tree API Contract

This specification documents the backend execution trace structure, the op-log request model, visual role mappings, hole policy, and API error formats for the Algorithm Laboratory simulation suite.

---

## 1. Request Models

The `/tree` endpoint operates in two mutually exclusive modes: **BST mode** (stateful history replayed via an op-log) and **Binary mode** (array-based level-order representation).

### 1.1 BST Mode: Op-Log Request Shape (`tree_type="bst"`)

BST operations maintain deterministic node identities statelessly through an append-only operation log.

- **Node Identity Rule**: The `id` of any node in the tree strictly equals the 0-indexed position `i` of the inserting op (`{"op": "insert", "value": ...}`) in `ops`. Node IDs are immutable and invariant across subsequent deletions and rebalances.
- **Duplicate Rule**: Inserting an already existing value into the tree is rejected with HTTP 400 (`field: "new_value"` or `field: "ops"`). Re-inserting a value that was previously deleted is permitted; it receives the ID of the new insert operation.

```json
{
  "algorithm": "bst_insert",
  "tree_type": "bst",
  "ops": [
    {"op": "insert", "value": 50},
    {"op": "insert", "value": 20},
    {"op": "delete", "value": 20},
    {"op": "insert", "value": 80}
  ],
  "new_value": 60
}
```

#### Deprecated Shim: `values` Array
For backward compatibility, requests supplying a legacy flat array `"values": [50, 20, 80]` are automatically converted by the backend into equivalent insert ops:
```json
[
  {"op": "insert", "value": 50},
  {"op": "insert", "value": 20},
  {"op": "insert", "value": 80}
]
```

---

### 1.2 Binary Mode: Array Shape (`tree_type="binary"`)

Binary mode represents trees via standard array layout:
- Root at index `0`.
- Left child of index `i` is at index `2i + 1`.
- Right child of index `i` is at index `2i + 2`.
- Parent of index `k > 0` is at `(k - 1) // 2`.

**Constraints**:
- **Prohibition of `ops`**: Because an op-log cannot encode null holes in fixed tree geometry, passing `"ops"` or `"values"` when `tree_type="binary"` is strictly rejected with HTTP 400 (`field: "ops"` or `field: "values"`).
- **Required Field**: Binary mode endpoints must provide an `"array"` field (e.g. `[10, 20, 30, null, 40]`).

```json
{
  "algorithm": "bst_traverse",
  "tree_type": "binary",
  "array": [10, 20, 30, null, 40],
  "order": "inorder"
}
```

#### Hole Policy & Orphaned Descendants
If an element in the array is `null`, any non-null slots at positions that descend from that `null` slot are orphaned (they have no structural parent).
- **Policy**: Orphaned descendants are dropped and not instantiated as nodes.
- **Reporting**: Dropped nodes are appended to a `"warnings"` list returned in the response:
  ```json
  "warnings": [
    "Orphaned descendant array[3] = 30 dropped because ancestor at array[1] is null"
  ]
  ```

---

### 1.3 Structural Comparison & Mirror Mode (`algorithm="bst_mirror"`)

The `bst_mirror` algorithm compares two trees (`tree_a` and `tree_b`) recursively. Each tree spec can independently be either BST op-log or binary array.

- **Modes**:
  - `mode="mirror"`: Tree A mirrors Tree B iff `root_a.val == root_b.val`, `left(A)` mirrors `right(B)`, and `right(A)` mirrors `left(B)`.
  - `mode="identical"`: Tree A equals Tree B iff `root_a.val == root_b.val`, `left(A)` equals `left(B)`, and `right(A)` equals `right(B)`.
- **Response Format**:
  ```json
  {
    "steps": [...],
    "final_tree_a": { "nodes": [...], "root_id": 0 },
    "final_tree_b": { "nodes": [...], "root_id": 0 },
    "verdict": {
      "is_match": true,
      "first_mismatch": null
    },
    "warnings": []
  }
  ```

## 2. Standard Error Format

Every error generated by the API—including bad inputs, schema mismatches, duplicate inserts, absent deletions, and unhandled exceptions—strictly conforms to:

```json
{
  "error": "<Descriptive error message>",
  "field": "<target_parameter_or_system_scope>"
}
```

Common field values:
- `"new_value"`: Missing, non-integer, or duplicate insert value.
- `"delete_value"`: Missing, non-integer, or absent delete value.
- `"target_id"`: Missing or absent node ID in `bst_height_depth`. If `target_id` is provided, the query searches exclusively by node ID; it returns HTTP 400 with `field: "target_id"` if absent, without falling back to `target_value`.
- `"target_value"`: Missing or absent target value in `bst_height_depth` (used only when `target_id` is absent).
- `"ops"`: Malformed op list, missing op fields, or forbidden in binary mode.
- `"array"`: Missing or invalid array in binary mode or array_to_tree.
- `"tree_a"`, `"tree_b"`: Missing, malformed, or invalid tree specification in `bst_mirror`.
- `"mode"`: Invalid comparison mode (must be `'mirror'` or `'identical'`).
- `"order"`: Invalid traversal order.
- `"tree_type"`: Invalid tree model (must be `'bst'` or `'binary'`).
- `"algorithm"`: Missing or unknown algorithm.
- `"body"`: Non-JSON or malformed HTTP request payload.
- `"request"`: HTTP-level errors such as 405 Method Not Allowed (e.g. GET /tree).
- `"server"`: Unexpected server error (HTTP 500 returns fixed message "Internal server error" and logs full traceback server-side).

## 3. Step Schema & Role Mappings

Every animation step generated by simulation algorithms conforms to the `make_step` trace specification.

### 3.1 Step Object Schema (Standard Single-Tree)

```json
{
  "type": "compare",
  "snapshot": {
    "nodes": [
      {
        "id": 0,
        "label": "50",
        "sublabel": null,
        "parent_id": null,
        "side": null
      }
    ],
    "root_id": 0
  },
  "annotation": "Human-readable explanation of the current operation",
  "highlighted": [],
  "comparing": [0],
  "rotating": [],
  "pruned": [],
  "new_node": [],
  "selected": [],
  "payload": {
    "path": [0]
  }
}
```

#### 3.1.1 Search and Insertion Path (`payload.path`)
- **Format**: `payload: { "path": [node_id_0, node_id_1, ...] }`
- **Semantics**: An ordered list of ancestor node IDs visited so far from the root down to the current node (`root` first).
- **Invariants**:
  - `path[0]` is always the root node (`parent_id == null`).
  - For each `i > 0`, `node(path[i]).parent_id == path[i-1]` (strictly forms an ancestor chain).
  - On `compare` steps during insertion and deletion search, `path` ends at the node currently evaluated.
  - On the final `insert` step, `path` ends at the parent of the newly attached node, allowing the client to keep the full path lit.

### 3.2 Dual-Tree Step Schema (Mirror & Structural Comparison)

Algorithms comparing two trees concurrently (`bst_mirror`) emit dual snapshots and suffixed role arrays (`_a` and `_b`):

```json
{
  "type": "mirror_compare",
  "snapshot_a": { "nodes": [...], "root_id": 0 },
  "snapshot_b": { "nodes": [...], "root_id": 0 },
  "annotation": "Comparing A:10 with B:10 — values equal",
  "comparing_a": [0],
  "comparing_b": [0],
  "matched_a": [],
  "matched_b": [],
  "mismatch_a": [],
  "mismatch_b": []
}
```

### 3.3 Visual Role Mapping (`DEFAULT_ROLES`)

The visualizer consumes semantic role arrays populated automatically from `node_ids`:

| Step Type | Primary Role Array | Meaning |
|---|---|---|
| `compare` | `comparing: [id, ...]` | Nodes currently participating in a comparison/search |
| `visit` | `highlighted: [id, ...]` | Node currently visited during traversal |
| `insert` | `new_node: [id]` | Newly attached node in tree |
| `create_node` | `new_node: [id]` | Node instantiated from array/input buffer |
| `delete_leaf` | `highlighted: [id]` | Leaf node designated for direct removal |
| `delete_single_child`| `highlighted: [id, child_id]` | Single-child node and child being promoted |
| `delete_two_children`| `highlighted: [id, succ_id]` | Two-child target and in-order successor to relink |
| `delete_done` | `highlighted: [id]` or `[]` | Completion of deletion; highlights new subroot/child |
| `reuse_node` | `highlighted: [id]` | Reusing existing prefix/node (trie) |
| `hash_compute` | `highlighted: [id]` | Slot computed during hashing |
| `probe` | `comparing: [id]` | Probing collision slots in open addressing |
| `mismatch` | `pruned: [id]` | Mismatched branch in pattern search |
| `prune` | `pruned: [id]` | Pruned search branch (backtracking / branch & bound) |
| `expand` | `highlighted: [id]` | Expanding frontier node |
| `call` | `new_node: [id]` | Recursive stack frame invocation |
| `dp_fill` | `new_node: [id]` | Table cell / subproblem value committed |
| `select` | `selected: [id]` | User-selected or inspected node |
| `mirror_compare` | `comparing_a`, `comparing_b` | Dual-node inspection in mirror comparison |
| `struct_compare` | `comparing_a`, `comparing_b` | Dual-node inspection in identical structural check |
| `mirror_match` | `matched_a`, `matched_b` | Nodes or dual-null positions successfully matched |
| `mirror_mismatch` | `mismatch_a`, `mismatch_b` | Position or value mismatch between Tree A and Tree B |

## 4. Deletion Protocol Details

BST node deletion strictly maintains node identity and pointer integrity:
1. **Search Phase**: Comparisons begin at the root node. The node being evaluated is placed in `comparing: [current.id]`.
2. **Absent Deletion**: If the target value does not exist in the tree, the request is rejected with HTTP 400 (`field: "delete_value"`).
3. **Two-Child Relinking**:
   - The in-order successor (leftmost node in the right subtree) is located.
   - The successor's node is physically relinked into the target node's position.
   - The successor preserves its original `id` (e.g. `succ_id = 3`), while the deleted node (`current.id`) is unlinked and removed.
   - The target node's value is never overwritten with the successor's value.
4. **Completion Step**: Deletion ends with a `delete_done` step highlighting the resulting position.

## 5. Dual-Panel Snapshot Contract (heaps and heapsort)

Heap algorithms show one logical structure twice: as a contiguous array (with its
sorted tail during heapsort) and as the complete binary tree encoded by that
array. Both panels are driven by a single `PlaybackController` step, so they can
never disagree about the current step.

### 5.1 Step shape

```json
{
  "type": "swap",
  "kind": "dual",
  "snapshot": {
    "array": {
      "cells": [
        {"id": 0, "value": 5},
        {"id": 1, "value": 9},
        {"id": 2, "value": 2}
      ],
      "heap_size": 3,
      "heap_type": "min"
    },
    "tree": {
      "nodes": [
        {"id": 0, "label": "5", "sublabel": "i=0", "parent_id": null, "side": null},
        {"id": 2, "label": "2", "sublabel": "i=2", "parent_id": 0, "side": "left"},
        {"id": 1, "label": "9", "sublabel": "i=1", "parent_id": 0, "side": "right"}
      ],
      "root_id": 0
    }
  },
  "swapping": [2, 0],
  "payload": {"from_index": 0, "to_index": 2},
  "annotation": "Swap 2 with 5 so the smaller value becomes the root"
}
```

### 5.2 Rules

- **`kind: "dual"`** marks a step whose `snapshot` has both `array` and `tree`.
  Single-panel tree steps keep `kind: "tree"` (AVL) and keep their existing
  top-level `snapshot` shape.
- **`snapshot.array.cells`** is ordered by array index. Each cell carries the
  element `id` and its integer `value`. Duplicate values are allowed; `id` is
  what identifies a cell.
- **`snapshot.array.heap_size`** is the number of cells inside the heap region.
  Cells at index `>= heap_size` are the sorted tail and are rendered outside the
  heap boundary. `heap_size` is the only positional state: it is never inferred
  from roles.
- **`snapshot.array.heap_type`** is `"min"` or `"max"`.
- **`snapshot.tree`** is the standard tree snapshot built from
  `cells[0:heap_size]` using the 0-based array encoding: left child `2i + 1`,
  right child `2i + 2`, parent `(i - 1) // 2`. `sublabel` is `"i=<index>"`.
- **Role arrays carry element ids, not indices**, and are valid for both panels.
  A consumer highlights an array cell and a tree node by the same id.
- **`payload`** carries the indices involved in the step (e.g. `from_index`,
  `to_index`, `focus_index`) for narration and tests, never for rendering.
- Element ids are assigned deterministically during stateless replay: each
  inserted value receives the next creation id; a `build` op assigns ids in
  array order. Swaps move ids, never rename them.

### 5.3 Why this shape

The two panels answer different questions: the array makes the index formulas
(and the sorted tail) obvious, while the tree makes the heap property and the
bubble path obvious. Keeping one step and one id space means Prev/Next and
Play/Pause act on both panels together, and a test can assert the tree is
exactly `cells[0:heap_size]` at every step.

## 6. Heap Trace Contract (`POST /heap`)

Heap traces are produced by a stateless op-log replay, exactly like BST mode:
the client keeps `ops`, sends them with one `action`, and renders the returned
steps. This keeps the backend free of session state and makes replay
deterministic.

### 6.1 Request shapes

Insert / extract / build (incremental heap):

```json
{
  "algorithm": "heap_op",
  "heap_type": "min",
  "ops": [{"op": "insert", "value": 5}, {"op": "insert", "value": 9}],
  "action": {"op": "insert", "value": 2}
}
```

Heapsort (whole array at once):

```json
{
  "algorithm": "heapsort",
  "heap_type": "max",
  "array": [5, 1, 9, 3, 7]
}
```

Rules:

- `heap_type` is `"min"` (default) or `"max"`.
- Ops are `insert` (`value` integer), `extract` (no fields), or `build`
  (`values` list). `build` is only valid as `ops[0]` or as the `action` of an
  empty heap; anything else is HTTP 400 with `field: "ops"` / `"action"`.
- Duplicate values are allowed everywhere. A swap happens only when the
  candidate is **strictly** better (`<` for min, `>` for max), so equal values
  never swap and traces are stable.
- Caps: at most 31 elements and 1000 steps. Exceeding either is a 400, never a
  500.
- `action` may be omitted. The response then contains `steps: []` and
  `final_state` describing the heap after replaying `ops` — useful for drawing
  the current heap without performing an operation.

### 6.2 Response shape

```json
{
  "steps": [ /* dual-panel steps, see §5 */ ],
  "final_state": { "array": {...}, "tree": {...} },
  "metrics": {"comparisons": 7, "swaps": 3, "steps": 18},
  "metadata": {"algorithm": "heap_op", "heap_type": "min", "heap_size": 4}
}
```

`final_state` is always the snapshot of the last step, so a client that only
wants the end result does not need to special-case it.

### 6.3 Step types

Every heap step has `kind: "dual"` and the snapshot shape from §5. Roles refer
to element ids and drive both panels.

| `type` | When | Notable `payload` | Roles |
| --- | --- | --- | --- |
| `append` | New element written to the next free index | `index`, `value`, `heap_size` | `new_node` |
| `compare` | Bubble-up parent check or sift-down child comparison | `child_index`/`parent_index` or `parent_index`/`left_index`/`right_index`/`chosen_index`, `focus_index` | `comparing` |
| `swap` | Two cells exchange positions | `from_index`, `to_index`, `from_value`, `to_value` | `swapping` |
| `insert_done` | Insert settled | `index`, `value` | `highlighted` |
| `extract_root` | Root about to be removed | `index`, `value` | `selected` |
| `remove_last` | Last cell popped after moving it to the root | `index`, `extracted_value`, `extracted_id`, `heap_size` | — |
| `extract_done` | Extract settled, new root named | `extracted_value`, `extracted_id` | `highlighted` (new root) |
| `build_start` | Bottom-up heapify begins | `n`, `last_parent` | `highlighted` (root) |
| `heapify_node_done` | Subtree at an index is a valid heap | `index` | `selected` |
| `build_done` | Whole array is a valid heap | `heap_size` | — |
| `mark_sorted` | One element frozen into the sorted tail | `sorted_from`, `heap_size` | `sorted` (tail) |
| `heapsort_done` | Sorted region covers the array | `sorted: true` | `sorted` (all) |

`compare` steps snapshot the structure **before** the swap they recommend, which
is why the invariant tests allow the compared edge to be temporarily violated.
Every `*_done` step must have zero violations.

### 6.4 Heapsort direction

Heapsort sorts the array in place using the selected heap type:

- `max` heap → ascending output (largest extracted to the end each round).
- `min` heap → descending output (smallest extracted to the end each round).

The sorted region grows from the right; `heap_size` shrinks to match, and the
`heap | sorted` divider in the array panel is placed at `heap_size`.

## 7. AVL Trace Contract (`POST /avl`)

AVL uses the same stateless op-log model as BST mode: the client keeps `ops`,
sends them with exactly one action, and renders the returned steps. The replay
of `ops` is silent, so a trace always describes one operation.

### 7.1 Request shapes

```json
{
  "algorithm": "avl_insert",
  "ops": [{"op": "insert", "value": 30}, {"op": "insert", "value": 20}],
  "value": 10
}
```

```json
{
  "algorithm": "avl_delete",
  "ops": [{"op": "insert", "value": 10}, {"op": "insert", "value": 20}],
  "value": 20
}
```

```json
{
  "algorithm": "avl_replay",
  "ops": [{"op": "insert", "value": 50}, {"op": "delete", "value": 10}]
}
```

Rules:

- `ops` entries are `insert` or `delete` with an integer `value`, applied in
  order. An insert of a live value and a delete of an absent value are rejected
  with HTTP 400 and `field: "ops"`, because the log must be consistent.
- `avl_insert` rejects a `value` already present (`field: "value"`);
  `avl_delete` rejects a `value` that is absent (`field: "value"`).
- `avl_replay` ignores `value` and returns `steps: []` plus `final_tree`, which
  is how a client draws the current tree without performing an operation.
- Node ids follow the same rule as BST mode: the id is the index of the
  inserting op. A value that is deleted and later reinserted receives the id of
  the new inserting op. Rotations relink nodes and never change an id.
- Caps: `MAX_AVL_OPS = 64` ops per request and `MAX_AVL_STEPS = 1000` emitted
  steps. Exceeding either is a 400, never a 500.

### 7.2 Height and balance factor

- Height is counted **in edges**: a leaf has height `0`, an empty child has
  height `-1`.
- Balance factor is `height(left) - height(right)`, so `+1` means left-heavy
  and `-2` is the start of the right-left/right-right territory.
- Every snapshot sets `sublabel` to `"bf:+N"` / `"bf:-N"` / `"bf:+0"`, computed
  from the links in that same snapshot. A rendered badge can therefore never be
  stale: it is not copied from a stored field that might lag a rotation.

### 7.3 Response shape

```json
{
  "steps": [ /* tree steps, kind: "tree" */ ],
  "final_tree": { "nodes": [ ... ], "root_id": 1 },
  "metrics": {"comparisons": 2, "rotations": 1, "steps": 8, "height": 2},
  "metadata": {"algorithm": "avl_insert"}
}
```

`final_tree` is always the snapshot of the last step, so the end result needs
no special case. `metrics.rotations` counts **single** rotations: an LR or RL
case contributes two.

### 7.4 Step types

Every AVL step has `kind: "tree"` and the single-tree `snapshot` shape
(`nodes`, `root_id`) from §3.1. Roles refer to node ids.

| `type` | When | Notable `payload` | Roles |
| --- | --- | --- | --- |
| `compare` | Search descends one level | `path` (ancestor ids, root first) | `comparing` |
| `insert` | New leaf linked to its parent | `path`, `value`, `node_id` | `new_node` |
| `balance_update` | Height/bf recomputed on the way back up | `node_id`, `value`, `height`, `balance_factor` | `highlighted` |
| `unbalanced` | First ancestor with `abs(bf) > 1` | `node_id`, `value`, `balance_factor`, `case` | `unbalanced` |
| `rotate_LL` | Left-left case: rotate right at the node | `case`, `phase`, `phases`, `unbalanced`, `pivot`, `new_root`, `subtree` | `rotating` |
| `rotate_RR` | Right-right case: rotate left at the node | same | `rotating` |
| `rotate_LR` | Left-right case, emitted twice | same, `phase` `1` then `2` | `rotating` |
| `rotate_RL` | Right-left case, emitted twice | same, `phase` `1` then `2` | `rotating` |
| `insert_done` | Insert settled | `value`, `node_id`, `rotations`, `height` | — |
| `delete_leaf` | Leaf unlinked | `value`, `node_id`, `path` | `highlighted` |
| `delete_single_child` | One child promoted | `value`, `node_id`, `replacement`, `path` | `highlighted` |
| `delete_two_children` | Successor relinked into place | `value`, `node_id`, `successor`, `path` | `highlighted` |
| `delete_done` | Delete settled | `value`, `rotations`, `height` | `highlighted` (root) |

### 7.5 Rotation replay

A rotation is shown as a sequence, not a single jump:

1. `unbalanced` with the **pre-rotation** snapshot, naming the case and the
   node whose `bf` left `[-1, 1]`.
2. One `rotate_*` step per single rotation. LL and RR rotate once; LR and RL
   rotate twice and carry `phase: 1|2` so a player can narrate "first make it
   left-left, then rotate right".
3. `rotation_done` on the balanced subtree, naming its new root, height, and bf.

Insert stops the retrace after its first rotation: in insertion the subtree
height returns to its pre-insert value, so no ancestor above can be unbalanced.
Delete keeps walking ancestors after a rotation, because removing a node can
shorten a subtree and expose a new imbalance higher up.

### 7.6 Invariants

The tests check every snapshot, not just the final one:

- The in-order walk is strictly increasing (no duplicates).
- `parent_id`/`side` links are consistent, with exactly one root.
- Every `sublabel` equals the balance factor recomputed from that snapshot.
- Node ids never change value within a call.
- Per plan D9, while an operation is in flight an unbalanced node is allowed
  only on the path from the operation focus to the root. Every
  `insert_done`/`delete_done` step must have **zero** nodes with `abs(bf) > 1`.

## Section 8 Trie Phase D

Request POST /trie body { algorithm, ops, action }. algorithm in {trie_insert,trie_search,trie_prefix}. ops committed history inserts only. insert action {word}; search {word}; prefix {prefix}.

Normalisation and limits: words lowercased server-side then must match ^[a-z]+$. Else 400 field word or prefix. Word length 1-12; at most 30 words in op log; at most 200 total trie nodes (else 400 field word). Autocomplete at most 10 completions (truncated true when more). Empty string: insert/search reject 400; prefix accepts empty (root, first 10 words alphabetically). Duplicates: inserting existing word 400 field word. Inserting car after card creates no nodes only marks end.

IDs: root 0; counter assigned in creation order during stateless replay; children ordered alphabetically. IDs pure function of op log.

Response { steps, final_tree, metrics, metadata }. Tree snapshot { nodes: [{id,label,parent_id,side:null,sublabel,terminal}], root_id }; root label root; others single letter. Metrics nodes words created reused letters_total compression. Metadata normalized_word or prefix, completions, truncated.

Step types all kind tree snapshot after step payload.path ancestor id chain.
Insert: per letter node_reused (reused:[id]) or node_created (created:[id]); payload {letter,depth,path,word}. Then mark_end (selected:[id]; payload {word,was_new_node}). Then insert_done (payload {created_count,reused_count}).
Search: per letter match (matched:[id]) or no_match (payload {letter,depth,failed_at}); outcome found/not_found (reason in {missing_edge,not_a_word}); then search_done.
Prefix: per letter match/no_match; full match prefix_matched (payload {prefix,node_id}) then prefix_done (selected terminal nodes of completions, matched prefix path, payload.completions at most 10, truncated). Missing edge prefix_missing then prefix_done empty.

Roles: created (new node, green, thick solid ring plus +), reused (blue, thin double ring), matched (check glyph), selected, new_node.

Caps MAX_TRIE_STEPS enforced 400 field word.

## Section 9 Hashing Phase D

Request POST /hash body { algorithm, hash_fn, table_size, probing, ops, action }. algorithm in {hash_insert,hash_delete,hash_search}. hash_fn in {sum_mod,poly}. probing in {linear}. table_size initial 5..13 default 7.

Hash functions: sum_mod h = sum char codes mod m. poly h = 0; for c h = (h*31 + code(c)) mod 2^32; index = h mod m. Test vectors m=7: sum_mod abc raw 294 idx 0; poly abc raw 96354 idx 6; ab and ba both idx 6 under sum_mod; poly ab 3105 idx 4; poly ba 3135 idx 6.

Keys strings 1-12 chars printable ASCII excluding whitespace codes 33-126 case-sensitive. Bad key 400 field key.

Limits: MAX_TABLE_SIZE 63. Growth new_size = 2*m+1 (7 to 15 to 31 to 63). Max live keys 40 (400 field key beyond). Max total ops 100.

Load factor and resize: chaining resizes when (n+1)/m > 1.0; open when (live+tombstones+1)/m > 0.75. Check before place. Resizes independent per panel. At cap in-place rehash same size clears tombstones. If still would exceed threshold 400 field key table at maximum capacity.

Duplicates absent: inserting live key 400 field key. Deleting absent 400 field key. Searching absent not error not_found step.

Tombstones open addressing: delete leaves visible tombstone snapshot slot {tombstone:true} rendered dagger plus hatch plus aria.
